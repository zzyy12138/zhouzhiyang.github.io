同样的模型、同样的知识库，提示词差一截，效果能差到让人怀疑人生。Dify 里提示词又常常和变量、检索结果绑在一起，所以我单独记了一篇「怎么写才不翻车」。

## 我拆成三块

1. **系统提示词**：角色、边界、风格、硬性规则
2. **用户侧模板**：把 `{{user_query}}` 和任务说明拼好
3. **上下文**：检索片段、历史对话、外部 API 结果

系统提示词尽量稳定；变的东西走变量。别把整份文档粘进系统提示词——又贵又难维护。

## 角色别空、任务别虚

空的：「你是一个智能助手，请友好回答。」
好一点的：

```text
你是公司内部的售后助理，只回答物流、退换货、保修政策。
不讨论无关话题。信息以检索片段为准；片段没有就说不知道，并建议转人工。
回答用简洁中文，必要时分点。
```

任务描述要可执行。「处理一下」不如「把下列 JSON 转成 Markdown 表格，只要 name 和 amount 两列」。

需要固定版式时，直接给骨架：

```text
按下面结构输出：
- 结论：
- 依据（引用片段要点）：
- 下一步建议：
```

## 和知识库一起用时

检索结果塞进提示词时，我会强调优先级：

```text
下列片段来自知识库，可能不完整或有噪声。
请只依据片段回答；发生冲突时以最近更新日期为准（若片段中有）。
没有依据时回复：知识库中未找到相关说明。

片段：
{{knowledge_base_results}}

用户问题：
{{user_query}}
```

片段太长就调检索 Top K / 分块，而不是让模型「自己看着办」——看着办的结果通常是幻觉。

## 变量

常见写法：`{{variable}}`、`{{obj.field}}`。知识库列表类变量按你当前 Dify 版本的模板语法迭代（有的支持循环标签）。

注意默认值：上游为空时，提示词里会出现空白段落，模型会开始脑补。必要时在代码节点先判断空结果，换一条「无检索」专用提示词。

## 优化时我真正改的方向

**更清楚**：用「必须 / 不要」代替「尽量 / 也许」。
**更可验**：要求「不确定就标明」，比强行自信好。
**更省 Token**：删客套、删重复、上下文只留相关句。
**少堆形容词**：「非常专业、极其详尽、全面深入」对模型没帮助，对账单有帮助。

改提示词一定留测试集：10～20 个真实问题，改完回归。凭感觉改三版，经常会改回去。

## 几个场景模板（可直接改）

**问答**

```text
你是 {{domain}} 领域的答疑助理。
依据片段回答，禁止编造。多要点时分点。
片段：{{knowledge_base_results}}
问题：{{user_query}}
```

**短文生成**

```text
主题：{{topic}}
受众：{{audience}}
篇幅：约 {{length}} 字
语气：{{style}}
用 Markdown。先给标题，再正文，最后给三句要点摘要。
```

**代码**

```text
语言：{{language}}
需求：{{requirements}}
约束：可运行、有关键注释、错误要处理；不要省略 import。
只输出代码块，解释放注释里。
```

## 常见翻车

- 规则互相打架（「简洁」又「面面俱到」）
- 不说失败怎么做，模型就硬答
- 上下文塞进大量无关聊天记录
- 把示例写太偏，模型只会模仿示例不会泛化——示例要短、要覆盖边界

提示词不是一次写完的艺术品，是和检索、模型、业务规则一起迭代的配置。我现在改应用，优先看失败案例，再动提示词，而不是先「优化文采」。
