## 跑起来之后才发现更难

十月把 vLLM、SGLang、量化练过一轮时，觉得服务起来了就算完。真正接业务才清楚：挂了好发现，慢了、贵了、答案飘了，往往更难处理。

LLMOps 这个词听着大，落到日常就几件事——稳不稳、问题找不找得到、变更能不能回滚、账单能不能讲清楚。下面是这段时间踩完坑之后的归纳，不是课表。

## 和以前做服务监控不太一样

以前排障多看 CPU、内存、接口错误率。推理服务还得多盯：

- 首 token 延迟（TTFT）比平均耗时更能反映对话体验
- 显存和 KV cache 往往比 CPU 先报警
- 变更不只换镜像，还可能动采样参数、Prompt、路由比例
- 成本是持续烧卡时，不是上线那天一次性的

光靠「进程在不在」不够。

## 实际把服务管住的几块

**机器和引擎。** 驱动、CUDA、K8s 调度、多卡拓扑；vLLM / SGLang 的并发和量化。运维阶段它们是被管对象：版本、并发上限、显存余量，比追新框架要紧。

**服务层。** FastAPI 网关做鉴权、限流、健康检查、灰度。业务直连引擎的时期，模型一换就要全员改配置，后来都收口到别名路由。

**观测和质量。** 指标、带 `request_id` 的日志，跨组件时再补链路。没有抽检的话，「没报错但在胡说」会发现得很晚。

**应用侧。** Dify 工作流 / Agent、知识库效果也会反噬底层；Cursor 之类能加快写巡检脚本，生产改动仍要人审。

ELK 三月到五月已经用熟，推理审计日志直接进同一套，没有另起监控栈。

## 日常里真正管用的习惯

早上看一眼夜间错误率和 GPU 空闲，比等业务反馈主动。有变更就小流量看 TTFT 和抽检，旧镜像先留着。复盘时写清是卡、模型、Prompt 还是下游工具，否则下次还是凭感觉。

后来固定下来的几件小事也很值：引擎补齐 `/health`、`/metrics`；网关日志带模型名和 token；「只切路由」和「回滚权重」两套路子随时能用。比再看一篇架构说明管用。
