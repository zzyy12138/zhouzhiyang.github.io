## 现状

两套能力一起用：

- **MCP**：给 Cursor / 终端 Agent 做运维只读与受限写操作
- **Dify**：给业务侧工作流、知识库、对外 API

有人问能不能「Dify 全改 MCP」或反过来。我们没并。

## 边界

| | MCP | Dify |
|--|-----|------|
| 用户 | 内部开发/运维 | 业务与终端用户 |
| 强项 | 宿主原生工具调用、IDE 内闭环 | 可视化编排、知识库、权限应用 |
| 风险面 | 工具过宽等于开后门 | 工作流与索引状态复杂 |

运维查询不进 Dify 工作流；业务问答不经过能切金丝雀的 MCP。身份和审计分开，省得一套 Key 打天下。

## 重复的部分

「查模型健康」在 MCP 和网关 HTTP 都有。保持网关为唯一真相源，MCP/Dify 都调网关，不各写各的探活。

协议越多，越要画泳道。MCP 不是 Dify 替代品，是另一类宿主的手；搅在一起，权限模型会先崩。
