Dify 里「建应用」不难，难的是选对类型，别用错容器。我这边的经验：先想清楚交互形态，再打开控制台。

## 三种应用，怎么挑

**对话型**：一问一答、客服、FAQ。配置集中在系统提示词、模型、可选知识库。适合验证「这事 AI 能不能答」。

**工作流型**：多步骤、分支、外部 API、要精确控制数据流。逻辑一复杂就上这个，别在对话应用里硬堆。

**助手型**：偏工具调用 + 多轮，适合「帮我查一下再算一下」这类。和具体版本能力绑定，用前先看当前环境支持哪些工具。

模糊需求时我通常：对话型一天内出原型 → 确认知识库和提示词 → 再决定是否迁移到工作流。

## 对话应用：我实际怎么配

1. 新建对话应用，名称写业务含义（「售后-物流查询」比「测试1」好找）
2. 写系统提示词：角色、边界、不会就说不会、输出风格
3. 选模型：日常用性价比高的；关键答复再上强模型
4. 挂知识库：Top K、阈值先保守
5. 开调试对话，用真实用户口吻测十几个问题

提示词里我会明确：

- 你是谁、服务谁
- 只能依据知识库 / 给定材料
- 不知道时怎么说（别编）
- 要不要列出步骤、要不要引用条目

参数方面：temperature 问答偏低；max tokens 按渠道限制（企业微信气泡太长没人看）。Frequency penalty 在重复套话明显时再加。

## 工作流应用：从客服骨架说起

一个还能看的骨架：

1. 开始：`user_query`
2. 知识库检索
3. LLM 生成回答（提示词注入检索结果）
4. 条件：若输出含「无法回答」或置信相关标记 → 走「转人工」文案；否则返回答案
5. 结束

提示词示例（可按业务改）：

```text
根据下列检索片段回答用户问题。没有依据就明确说不知道，不要编造。

片段：
{{knowledge_base_results}}

用户问题：
{{user_query}}
```

更复杂的数据分析类：代码预处理 → HTTP 拉数 → 再 LLM 写结论。外部依赖一定要有失败分支，生产环境尤其别省。

## 助手与工具

助手强在「模型决定何时调用工具」。工具可以是 HTTP、代码、查询类能力。设计时把工具描述写清楚——模型是靠描述决定调不调的，描述含糊就会乱调或从不调。

权限和副作用大的操作（删数据、发短信）不要轻易给自动工具，至少二次确认或人工节点。

## 配置项里我关心的

- **访问**：是否公开、是否要密码、是否开 API
- **多轮**：上下文轮数不是越大越好，又贵又容易跑偏
- **流式输出**：面向聊天 UI 建议开，体感好很多
- **内容安全 / 限流**：对外部用户开放时尽早开，别等被刷爆再补

## 测试别走过场

对话：单轮准确性、多轮是否忘上下文、空输入和超长输入。
工作流：每个节点输出看一眼；专门测失败分支（接口 500、知识库空结果）。
发布前我至少确认：关键路径手动走通、错误提示人话、Token 消耗量级心里有数。

发布后看调用量、错误率、平均耗时。异常飙高优先查模型供应商和知识库索引状态，其次才是自己的提示词回归。

版本上能写 changelog 就写一句「改了什么」——一个月后的自己会谢谢现在的自己。
