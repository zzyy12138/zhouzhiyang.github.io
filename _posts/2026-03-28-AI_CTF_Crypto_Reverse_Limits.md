## 实测体感

在授权题目上反复跑了一段时间后，体感很固定：

**相对擅长**

- 经典编码/古典密码、明确算法的脚本实现
- 根据报错迭代修补 Python 解密脚本
- 在给出二进制/源码片段时，解释函数大致在干什么

**容易装懂**

- 没有中间结果就「猜」密钥或协议细节
- 对混淆/强壳一上来编造控制流
- 算数/有限域细节口算出错，却写得很自信

所以流程改成：每一步必须落到**可执行验证**（跑脚本、看输出、对比样例），禁止连续多轮纯口头定论。

## 提示词里强制的几条

```text
你在参加授权 CTF。
只使用题目提供的附件与允许的本地工具。
每次给出命令或脚本后，等待执行结果再继续。
如果缺少关键材料，直接说缺什么，不要编造 flag 格式以外的「已破解」结论。
```

输出要求带：当前假设、下一步要跑的命令、成功/失败判据。没有判据的步骤一律驳回。

## 工具上的配合

- 密码题：本地 `python` + 明确依赖，stdout 截断到有用行
- 逆向：先 `file` / 字符串 / 反编译摘要，再让模型读**摘要**而不是一次性贴几 MB
- 模型上下文满了就总结「已否决路径」，避免反复试同一失败命令

## 和运维工作的关系

这套「假设 → 工具验证 → 记录」和推理服务排障其实同构。差别只是对象从 GPU 日志换成了题面。研究价值之一，是把 Agent 的胡言用机制压下去，而不是指望换一个更强的模型就万事大吉。
