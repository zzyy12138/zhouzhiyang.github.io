前面把功能拆开写了。这篇收一点「我真的会按这个做」的做法，加三个常见案子，以及翻车时怎么拆。

## 设计上的取舍

- **先小后大**：对话应用验证知识库和提示词，再迁工作流
- **提示词写边界**：不会就说不会，比热情幻觉强
- **检索优于措辞**：召回不对时先别改文采
- **贵操作放后面**：先规则/小模型分流，再大模型生成
- **失败可见**：降级要让用户或日志知道，别装没事

提示词对比我常挂在嘴边：

```text
# 差
写个代码

# 好一点
用 Python 3.10 写函数 parse_order(text) -> dict，
抽出 order_id 与 amount；解析失败抛 ValueError。
只输出代码，含类型注解。
```

## 知识库：少踩雷的习惯

- 文档按主题拆库，别一个库塞全世界
- 扫描版 PDF 先 OCR 或换源
- chunk 500～1000、overlap 50～100 当起点，用检索测试调
- 专有名词多就上混合检索
- 过期制度文件及时下线

## 案例一：内部智能客服

**目标**：物流 / 退换货 / 保修，答不上来转人工。

**做法**：

1. 两个知识库：政策文档、历史 FAQ
2. 工作流并行检索 → LLM 回答
3. 命中「投诉/索赔/起诉」等词直接转人工文案
4. temperature 偏低；回答要求带「依据摘要」方便质检

**踩坑**：一开始 Top K=8，模型东拼西凑。后来 Top K=3 + 提高文档质量，准确率体感明显好于继续堆模型。

## 案例二：内容生成流水线

**目标**：运营给主题，出 Markdown 初稿。

**做法**：

1. 开始节点收 topic / audience / length
2. 知识库取产品卖点
3. LLM 先出大纲，人工或自动确认（自动就加长度/标题检查）
4. 第二段 LLM 扩写
5. 代码节点做简单违禁词扫描

**取舍**：两段模型比一段「写篇完美长文」可控；成本略高但返工少。初稿用中档模型，定稿再上强模型也行。

## 案例三：数据分析助手

**目标**：自然语言查内部指标，出简短结论。

**做法**：

1. LLM 把问句收成受控查询（指标名、时间范围）——只允许白名单字段
2. HTTP 调内部查询 API
3. 代码节点做基本聚合
4. LLM 写「结论 + 注意口径」

**红线**：不要让模型直接拼 SQL 裸奔生产库。白名单和 API 层鉴权必须有。

## 问题排查速查

**检索不准**
看命中片段 → 调分块 / 文档 → 再调 Top K 与阈值 → 最后才换 Embedding。

**工作流慢**
看各节点耗时；并行化独立 IO；砍提示词长度；检查是否在循环里打大模型。

**成本飘**
开发环境换便宜模型；给迭代加上限；缓存稳定 FAQ；盯日 Token 曲线。

这三块里，八成问题其实是「文档和流程」而不是「平台不会用」。
