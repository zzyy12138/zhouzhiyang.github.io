基础流会画之后，业务会把你推向并行检索、分支策略、失败降级。这阶段容易画成蜘蛛网。我的原则：**先正确，再并行；先可观测，再炫技。**

## 列表与循环

对一批条目分别调用 LLM / HTTP，常见两种做法：

1. **代码节点里循环**（适合轻量、可在沙箱完成的逻辑）
2. **平台迭代节点**（版本若提供，适合跟下游 LLM 节点组合）

代码示意：

```python
results = []
for item in items:
    # 这里通常只做清洗/拼装；重活交给后续节点或外部服务
    results.append({"id": item["id"], "text": item["text"].strip()})
return {"results": results}
```

注意费用与超时：迭代调用大模型时加上硬限制（最大 N 条），别让用户上传 1 万行 CSV 直接打爆配额。

## 并行：真能省时间的时候再用

典型：同一个 `query` 同时打「产品知识库」「FAQ 知识库」「内部 HTTP 接口」，再合并给 LLM。

设计要点：

- 下游合并节点要能接受「某一路失败」
- 设好各路超时，避免一路拖死全局
- 合并后做裁剪，别把三路全文无脑塞进提示词

并行不是越多越好。三路里两路结果根本不用，只是在烧 embedding 和 API。

## 分支：按用户 / 风险分流

例子：`user_type == vip` 走强模型 + 更大 Top K；普通用户走便宜模型。
或：情感/关键词命中投诉 → 固定「转人工」话术，不再自动乱答。

条件尽量简单可测。复杂规则先放代码节点算出 `route=a|b|c`，再用条件节点分流，比在条件框里写长表达式好维护。

## 错误处理：重试 vs 降级

值得重试的：超时、429、偶发网络错误。
不值得死磕的：401（Key 错）、业务 400（参数错）。

策略我一般是：

- 节点级：有限次重试 + 间隔
- 流程级：失败分支返回友好文案或缓存/兜底
- 模型挂了：切备用模型或「稍后重试」，而不是空响应

降级示例：知识库超时 → LLM 仅用通用政策提示，并标明「未能检索知识库」。用户至少知道系统降级了，比一本正经瞎编好。

## 高级节点用法

**代码节点**：清洗、聚合、简单统计可以；别指望重度 pandas/numpy 环境（看沙箱实际允许的库）。重分析丢到你们自己的分析服务，HTTP 调回来。

**HTTP 节点**：把鉴权、超时、非 2xx 怎么处理想清楚。响应用 JSON 解析后只取需要字段，减小后续 Token。

**变量节点**：做标志位、拼默认值、统一输出 schema，让结束节点稳定。

## 一个还算现实的客服流

1. 收问题
2. 并行：产品库检索 + FAQ 检索（可选：情绪/意图分类）
3. 若命中高风险词 → 转人工文案
4. 否则 LLM 生成
5. 简单质检（代码或二次 LLM）：过短 / 含「我胡编」类模式则重试一次或转人工
6. 落库 / 打日志（HTTP）

质检别套娃三次 LLM，成本和控制复杂度会爆。

## 调试

- 单节点测输出结构
- 看运行历史里每步耗时，找瓶颈
- 性能差时先问：是模型慢、检索慢，还是自己串行太多

可维护性上：模块化子流程（能拆应用就拆）、节点命名带业务含义、关键分支写注释。三个月后能看懂，比当时少两个节点更重要。
