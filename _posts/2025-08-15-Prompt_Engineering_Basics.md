提示词工程听着玄，落地就是：把任务说清楚，让模型少猜。好提示能少重试、少花 token；烂提示再强的模型也会跑偏。下面是反复验证过的写法，不是教条清单。

## 一条提示通常有什么

多数有效 prompt 可以拆成四块（不必每块都出现）：

1. **角色 / 上下文** — 希望模型以什么立场答
2. **指令** — 具体要做什么
3. **输入** — 待处理的原文、数据、用户问题
4. **输出约束** — 格式、长度、禁止事项

模糊的「处理一下」几乎必翻车；「用三条 bullet 总结下面文档的风险点，每条不超过 20 字」成功率高很多。

## Zero-shot / Few-shot / CoT

**Zero-shot：** 只给指令。模型够强、任务够常规时够用，也省 token。

**Few-shot：** 塞 1～5 个输入输出样例，让它抄格式。分类、抽取、固定 JSON 结构时特别管用。样例要准、要覆盖边界情况；顺序从简单到难。样例太多有时反而干扰，3 个左右先试。

```text
将情感标为 positive / negative / neutral。

文本：物流很快，包装完好。
标签：positive

文本：屏幕有亮点，客服不回。
标签：negative

文本：{{user_text}}
标签：
```

**Chain-of-Thought：** 要求先写推理再给答案。数学、多跳逻辑、需要排查条件的题，加一句「逐步推理，最后一行写最终答案」往往比堆样例更有效。注意：对外产品有时不想暴露推理过程，可以内层 CoT、外层只回结论。

## 常用技巧

**角色不是装饰。** 「扮演资深 Python reviewer」会改变用词和关注点；但角色再大也不能代替具体任务说明。

**用分隔符包住用户输入。** 减少指令被「污染」：

```text
根据 <<<DOC>>> 内的内容回答问题；不要编造文档没有的信息。

<<<DOC>>>
{{document}}
<<<END>>>

问题：{{question}}
```

**锁输出格式。** 要接程序就明确 JSON schema，并给一个合法例子。模型偶尔会加解释性废话，可以加「只输出 JSON，不要 Markdown 代码块」——仍不稳时，用响应解析 + 重试兜底。

**加硬约束。** 「不超过 200 字」「只谈技术、不谈报价」「不确定就说不知道」。幻觉没法靠提示根治，但可以把乱编空间压小。

## 三种常见骨架

问答（带检索上下文）：

```text
角色：内部技术支持。只依据「上下文」回答；上下文不足时明确说无法确定。

上下文：
{{chunks}}

问题：{{q}}
```

生成类（文案 / 邮件）：写清主题、受众、语气、长度，比形容词堆砌有用。

分析类：要求先列观察再给结论，并规定章节名——方便后处理，也方便人眼扫。

## 怎么迭代（别神话 A/B）

循环很朴素：写一版 → 固定 20～50 条真实 case → 看失败模式（跑题、格式碎、太啰嗦）→ 改一处再测。一次改太多变量，分不清是哪句生效。

温度和提示是耦合的：要结构化抽取，温度开很低；要头脑风暴，再升温。提示再好，采样参数拧飞了也会废。

## 踩过的坑

- 指令互相矛盾（「尽量详细」又「一句话」）
- 把业务规则埋在超长背景里，模型抓不住重点——规则应前置、加粗或编号
- Few-shot 样例本身有错，模型会认真学错
- 过度依赖「请认真思考」这类空话，不如把评分标准写死

提示词是产品逻辑的一部分，该进版本管理。和模型版本一起记：换了 Claude / GPT / 自家微调模型，同一套 prompt 往往要重调一截。
