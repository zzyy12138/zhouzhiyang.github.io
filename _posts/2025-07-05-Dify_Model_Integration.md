模型是 Dify 里最烧钱也最影响体感的一块。配置模型时，优先顺序是：**数据能否出网 → 延迟 → 效果 → 单价**。

## 控制台里怎么加 Provider

以 OpenAI 兼容接口为例：进设置 → 模型供应商 → 填 API Key / Base URL → 拉可用模型 → 保存后在应用里选用。

国内中转或 Azure，重点核对 Base URL 和模型名是否和供应商文档一致。Key 没问题但模型名写错，报错信息有时很含糊。

Anthropic、通义、文心等同理：先在供应商控制台确认额度与区域，再进 Dify。

## 怎么选聊天模型（实用向）

- **强模型（如 GPT-4 类）**：复杂推理、挑剔的写作、关键客服终审
- **性价比模型（3.5 / 小参数快速版）**：分类、改写、大量日常问答
- **本地模型**：内网、合规、想控成本；效果和运维自己扛

别全站顶格强模型。「意图分类」用强模型是典型浪费。

### 常改的参数

- **temperature**：问答 0.2～0.5；创意写作再升高
- **max tokens**：按渠道截断，避免又慢又贵
- **top_p**：多数情况默认就行，别和 temperature 一起猛拧

可以存几套「场景预设」：准确 / 均衡 / 发散，应用里按场景套，比每次手滑改参数稳。

## 本地：Ollama 用得最多

```bash
# 机器上
ollama pull llama3
# 默认 API
# http://localhost:11434
```

Dify 里把供应商指到 Ollama 地址，选对应模型名。Docker 部署时注意：**容器访问宿主机 Ollama** 不是 `localhost`，Linux 上常见要写成宿主机 IP 或 `host.docker.internal`（视环境而定）。接本地模型时，这一点最容易卡住。

LocalAI / vLLM 则走 OpenAI 兼容入口，Base URL 指到 `/v1`，模型名用实际加载的那个。GPU 显存不够时先量化模型，别先怀疑 Dify。

## Embedding 单独说

聊天模型和 Embedding 不是一回事。知识库用的 Embedding 决定召回质量。

- 云端 embedding：省事，按量付费
- 中文为主、要私有化：BGE / M3E 等值得试

换 Embedding = 知识库基本重来。选定前用一小批文档做检索对比，再全量建设。

## 切换与降级

工作流里可以按条件选不同 LLM 节点（VIP / 普通，简单 / 复杂）。
供应商挂了怎么办：准备备用 Provider 或本地模型，失败分支切过去，并打日志——否则界面上只能看到「用户说 AI 挂了」。

成本控制：

- 开发环境默认便宜模型
- 精简提示词和检索片段长度
- 对高频且答案稳定的问题做缓存（应用外或网关层）

## 监控看什么

调用次数、Token、错误率、P95 延迟。哪天账单暴涨，多半是：循环节点没限流、提示词塞了整页检索、某客户端在重试风暴。先查这三样。
