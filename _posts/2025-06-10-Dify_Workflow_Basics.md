工作流是我用 Dify 的主战场。对话应用适合快速验证提示词；一旦出现「先检索再判断再调接口」，我基本都会切到工作流，否则配置会拧成一团。

## 三个基本概念

**节点**：干一件具体的事——调模型、查知识库、跑代码、发 HTTP、做条件判断等。

**连线**：数据从上游流到下游。条件节点会分出 True/False（或多分支）路径。

**变量**：开始节点定义输入；中间节点产出中间结果；结束节点决定对外返回什么。引用语法一般是 `{{variable_name}}`，对象字段用 `{{obj.field}}`。

名字一定要起明白。我早期用过一堆 `output`，后面改流程时完全不敢动。

## 常用节点（按使用频率）

### 开始 / 结束

开始节点声明输入：文本、数字、文件等，哪些必填。结束节点挑选要输出的字段——API 调用方拿到的就是这里映射的内容。

### LLM

选模型、写系统提示词和用户提示词、调 temperature / max tokens。
准确问答我会把 temperature 压到 0.2～0.5；需要一点文采再往上加。别一上来就拉满 1.5，输出会飘。

### 知识库检索

输入查询文本，选知识库，设 Top K 和相似度阈值。输出是片段列表，通常要再喂给 LLM，而不是直接当最终答案甩给用户。

### 代码执行

适合 JSON 解析、列表拼装、简单规则。别指望在沙箱里随便 `pip install` 或读本机文件——权限和依赖都有限。复杂逻辑能抽到外部服务就抽。

### HTTP 请求

对接内部 API、Webhook。注意超时和鉴权头；失败时最好有分支或默认值，否则整条链路直接红。

### 条件判断

等于 / 包含 / 数值比较 / 正则都够用日常。复杂布尔别写在一个表达式里拧成麻花，拆成两级条件更清晰。

### 变量赋值

做中间态、拼默认回复、记标志位。小改动用赋值节点，比再挂一个 LLM「帮我改一下变量」便宜得多。

## 第一个有用的流：检索问答

顺序很简单：

1. 开始：`user_query`
2. 知识库检索：query = `{{user_query}}`，Top K 先 3
3. LLM：把检索结果塞进提示词，明确「找不到就说不知道」
4. 结束：输出 `answer`

提示词里我会写死两条规矩：只依据检索内容；检索为空时不要编。否则模型很爱「热情地胡说」。

## 稍复杂一点：带分支

常见模式：

1. 预处理（代码节点清洗输入）
2. HTTP 调业务接口
3. 条件：成功走 LLM 生成说明；失败走变量节点返回固定错误文案
4. 结束

循环类需求（对列表逐条调用 LLM）可以靠代码节点批量处理，或用平台提供的迭代类节点（视版本而定）。注意并发和费用——对 100 条长文本逐条 GPT-4，账单会很刺激。

## 变量这块容易栽的坑

- 上游没跑到，下游引用的变量是空的，LLM 提示词会缺上下文
- 数组 / 对象结构要和节点实际输出对齐，别想当然
- 结束节点漏选字段，API 侧看起来像「成功但没内容」

调试时我习惯：每加一个节点就跑一次，看输出面板，而不是画完整张图再测。

## 错误处理（基础版）

HTTP / 模型偶发失败很正常。节点上能开重试的先开（次数别太大，避免雪崩）。关键路径加失败分支：检索失败 → 固定兜底话术；API 失败 → 返回「稍后重试」而不是堆栈信息给用户。

## 几点个人习惯

- 一个节点只做一件事，别在代码节点里写小说
- 先串行跑通，再考虑并行（高级篇再写）
- 提示词和知识库质量，往往比再加两个节点更管用
