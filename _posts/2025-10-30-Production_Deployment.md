## 生产不是「多加几台同样的机器」

单机 vLLM 能聊，和线上能睡安稳，中间差的是：挂了谁发现、慢了怎么降级、换模型怎么回滚、账单能不能讲清楚。引擎跑通之后，生产侧真正要补的是这些运维能力，而不是再换一个启动命令。

## 架构上我坚持的几条

**业务不直连引擎。** 前面放自己的 API 网关（鉴权、限流、模型别名、`request_id`）。引擎地址、权重版本只在网关后切换。

**推理实例可复制。** 配置进环境变量 / ConfigMap，本地不攒脏状态；就绪探针要真能反映「模型已加载可服务」，而不是进程起来了就接流量。

**核心模型独占卡。** 共卡省钱但抖动明显，SLO 紧的我倾向于独占；长尾再分时或共卡，并且压测过。

**队列硬上限。** 超限 429 或排队超时，好过显存打爆集体 OOM。引擎和网关两边都要有并发概念。

多实例前面用负载均衡即可。策略不必花：轮询或最少连接都能起步；关键是健康检查要踢掉「进程在、模型没加载完 / 已经卡住」的节点。

## 发布：灰度比勇气重要

换量化档、换基座、改默认 `max_tokens`，都当变更。

1. 新版本小流量（金丝雀）
2. 盯 TTFT、错误率、抽检质量，不只看 5xx
3. 有问题只切路由回旧权重/旧引擎
4. 旧镜像和旧引擎先留着，别发完就删

我吃过「全量换量化、工具调用偶发坏掉」的亏，没有小流量对比，回滚都心虚。

## 监控最低配

- 可用性：非 5xx、非超时
- p95 TTFT、流式是否完整结束
- GPU 利用率 / 显存 / 温度（降频能解释「没改代码却变慢」）
- 按模型名聚合的请求量和 token

日志带 `request_id`、模型名、耗时。告警先抓：服务探活失败、错误率飙、TTFT 持续超线、显存逼近上限。通道用团队已经在用的（飞书/钉钉之类），别搞一套没人看的邮箱。

## 故障时先降级，再细查

经验顺序：

1. 确认是网关、引擎还是下游工具
2. 能切 stable / 缩 QPM 就先止血
3. 再查是否 OOM、共卡、上下文暴涨、错误的金丝雀

降级可以很土：大模型切小模型、缩短 `max_tokens`、关掉贵的工具调用、低优先租户先排队。土，但有效。

安全上也别迷信内网：网关要鉴权、限流，管理端口别裸露；日志里的用户输入按合规要求脱敏或控留存。

## 容量别拍脑袋

用真实 prompt 长度和峰值 QPS 估卡数：权重 + KV + 余量。闲时很低的卡是浪费，长期打满是事故预备役——看利用率调扩缩，比固定「我们有八张卡」有用。

十月如果只做一件和生产相关的事，我会选：引擎前面加网关 + 健康检查 + 能只切路由的回滚。有了这三样，后面的观测和 SLO 才接得上；没有的话，引擎再快也只是单机 demo。
