## 这两个月实际在干什么

六月初把 Dify 装起来，到七月中旬已经有业务工作流跑在上面。中间不是按章节学完，而是被具体问题推着走：流程怎么搭、知识库为啥答歪、API 怎么给前端、生产怎么别单点。

这篇只记结论和翻过的车。

## 平台本身：我怎么定位它

Dify 适合把 LLM、检索、HTTP、代码节点拼成可交付应用，比从零写编排快。它不替代推理集群——模型不稳定时，怎么改工作流都救不回来。

用下来比较稳的边界：

- 流程固定、要审计 → 工作流  
- 分支很多、要调外部工具 → 再考虑 Agent（当时还浅用）  
- 知识库先解决「有没有文档依据」，别指望它单独解决胡话  

## 工作流上踩过的

节点并非越多越强。早期把清洗、判断、多次 LLM 串很长，延迟和费用一起涨，排障也难。后来改成：规则能做的先规则；LLM 只放真正需要生成的位置；变量命名统一，避免下游取错字段。

循环和并行能用，但要给失败出口。HTTP 节点超时、非 2xx 处理没设计好时，整条流会「假成功」。

## 知识库

切太碎答案拼不起，切太整噪声大。TopK 凭感觉加大，只会让 prompt 又贵又吵。文档更新后索引没跟上，会出现「后台已改、模型还在背旧段」。

比较管用的习惯：元数据带上文档名和更新时间；重要应用钉住知识库版本，不在生产里随手改检索参数。

## API 与集成

给前端和脚本统一走应用 API Key，权限按应用收。流式和超时要在网关/反代侧一起验证，只在 Dify 控制台点试用不够。

本地模型、云端模型混用时，模型名和能力开关（工具调用等）要对齐，不然工作流在测试环境正常、生产偶发失败。

## 生产上留下的做法

- Docker 部署可以起步，注意组件依赖和数据卷备份  
- 配置和密钥进环境变量，别写进可提交的 `.env` 样例  
- 监控至少有：容器健康、工作流失败率、上游模型延迟  
- 变更先在测试应用验证，再切生产  

## 这两个月结束后的判断

Dify 能加快交付，但效果上限仍取决于模型质量和知识整理。工作流宜短、宜可观测；知识库要当产品内容来维护，不是上传完就结束。后面接自建 vLLM 时，这些判断仍然适用。
